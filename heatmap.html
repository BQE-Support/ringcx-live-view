Methodology & scope notes

Data source

Calls come from RingCentral's platform Call Log API (/restapi/v1.0/account/~/call-log) — not RingCX/ACE's session-token-only endpoint, which requires an internal-only permission no self-service app can obtain. Email and Webform come from Zendesk ticket creation timestamps, identified via the ticket's Origin field (mirrored as a tag) rather than Zendesk's native channel field, which is unreliable for this account (most tickets arrive through a middleware/API layer that reports every channel as api regardless of true origin).

Timezone & averaging

  • All day-of-week and hour-of-day bucketing uses Pacific Time, matching BQE's HQ business hours — not the caller's local time or UTC.
  • With no week selected, each matrix cell shows an average: total volume in that day+hour bucket ÷ number of times that weekday has occurred so far this year (not a raw total), so a partial year doesn't understate later months.
  • Selecting a week switches every cell to that week's actual count instead — hover any cell to see the exact value, how it compares to that slot's own YTD average, and its percentile among all 168 slots currently shown.

Color scale

  • The green-to-red scale is fixed, not rescaled per view: the reference maximum is computed once from every channel's full year-to-date matrix, so a given shade of red represents the same absolute volume whether you're looking at All, Calls, Email, or Webform, any direction filter, or any selected week. Switching views never silently changes what "red" means.
  • A single unusually busy week can exceed the fixed reference (which is based on YTD averages) — those cells simply clip at full red rather than the scale stretching to fit, which is standard behavior for a fixed-scale heatmap.

Heat by: metric toggle

  • Volume (default) works with any channel. Abandon Rate and Avg Handle Time are Calls-only concepts (they use the call's own result/duration fields) — disabled outside the Calls channel, auto-reverting to Volume if you switch away while one is active. First Response Time is a Zendesk-ticket concept with no meaning for Calls — disabled on the Calls channel, same auto-revert behavior.
  • Switching the metric only changes what the matrix and its legend show — the KPI tiles above (including Busiest Slot) always reflect Volume, regardless of which metric is currently heat-mapped.
  • An empty cell (no calls/tickets in that slot at all) is shown blank rather than as a misleading "0%" or "0s" — hover it to confirm "No data in this slot" rather than reading a blank cell as a real zero measurement.

Comparison & anomaly flagging

  • Once a week is selected, Compare to sets what "typical" means for every cell's tooltip delta: YTD average (default), the Previous week, or a Prior 4-week average. If there isn't enough history yet for the chosen mode (e.g. the earliest week on record), it falls back to YTD average with a note rather than showing nothing.
  • A white ring around a cell flags an anomaly: that week's actual value is more than 2 standard deviations above everything this exact day+hour slot has ever recorded (at least 4 prior weeks of history required before flagging — too few data points make a standard deviation meaningless). This is a different question from the Compare-to delta above — it's independent of which comparison baseline is selected, and only appears once a week is chosen.
  • Same week last year isn't available as a comparison option — the pipeline only holds year-to-date data; adding it would mean backfilling roughly 7 months of prior-year data across every pull script, deferred for now.

Custom date range, click-to-drill, export

  • The week dropdown and the two date pickers are mutually exclusive — picking one clears the other. A custom range works everywhere a week did (matrix, KPIs), except Compare-to and anomaly flagging are single-week-only and are disabled while a range is active.
  • Click any matrix cell to list the actual calls/tickets behind that number, scoped to whatever's currently in view. With no week/range selected this can span every occurrence of that slot all year — the list caps at 300 rows (most recent first) with a note; the panel's own "Export this slot (CSV)" button downloads the complete set, not just what's rendered.
  • Calls show time, direction, duration, and outcome — there's no clean per-call "agent" (a call's routing can end in a queue, auto-attendant, or a forwarded external number, not always one named person). Tickets (Email/Webform) show the Zendesk assignee and subject instead — every phone call also creates a Zendesk ticket, so "who handled this" lives on the ticket side, not the raw call record.

Day × Hour Agent Coverage Heatmap (Phase 4, 2026-08-05)

  • A separate heatmap below the Volume one (not a "Heat by" toggle, so both can be read side by side) showing how many agents are scheduled to be working each day+hour slot, from the Smartsheet Support Roster + PTO Calendar — not live presence (there's no real-time cross-check against Zendesk/RingCentral agent status yet, see below). With no week/range selected it shows the typical schedule (PTO ignored); selecting a week or range applies each date's actual approved PTO/holidays, so a past OR upcoming week (the dropdown includes the next 12 weeks even with no volume data yet) shows real expected coverage.
  • Calls restricts to phone-capable agents (the Roster's Phone checkbox — the real "who's in RingCX" signal, confirmed live; the sheet's separate "Support Type" field is blank on 105 of 109 rows and isn't it). Every other channel counts every agent with shift-time data, since all support engineers handle Zendesk tickets regardless of phone duty.
  • Shift length is a documented assumption: each agent's own Shift Start plus 8 hours — no Shift End column exists anywhere in the source sheet for any agent. Lunch is a documented assumption too: a 1-hour break starting at each agent's own Lunch Start, subtracted from their coverage for that hour — the sheet gives a lunch start time but, like shift length, no duration.
  • team members have no shift-time data anywhere in the sheet, and no reliable activity data to derive one from either — excluded from hourly coverage rather than guessed at: . (Agents on overnight rotations use the explicit shift blocks kept in the roster.)
  • PTO entries are matched to a roster employee by normalized name (case/spacing/punctuation-insensitive) — PTO entries couldn't be matched to a roster employee and are excluded from the coverage subtraction (undercounting PTO impact slightly rather than risking attributing time off to the wrong person; almost all are pre-2023 entries for employees no longer on the current roster). Company-wide entries (blank name, or "Holiday"/"Office Closed Holiday" typed into the name field) reduce every scheduled agent's count for that date. Team/region-level holidays reduce just that office — found live 2026-08-05 that some Holiday-type rows name a team ("PHL Support Team", "MX") rather than a person; these now correctly zero out only that office's scheduled agents on that date, not everyone.
  • Compare-to only offers "YTD average" for Coverage (Previous week/Prior 4-week don't add information over a schedule that's already fixed and known), and anomaly flagging is off entirely — a coverage dip from approved PTO is a known, planned fact, not a statistical surprise.
  • Planned vs. Actual: "Planned" is the Roster+PTO schedule described above. "Actual" (2026-08-05: "this data should be picked up with the daily dashboard refresh") shows how many agents had real ticket activity (a ticket created or solved, attributed to its assignee) in that exact day+hour slot, at least 3 times YTD - a documented threshold so a single incidental after-hours touch doesn't look like a regular pattern. This is derived entirely from data already pulled daily, not a live presence poller - Zendesk's Agent Availability API and RingCentral's extension presence are both real-time-snapshot-only with no historical query, so neither could be reconstructed from a once-daily pull; a true login/logout poller remains a possible future follow-up with its own always-on schedule. "Actual" reflects the whole year's empirical pattern and does not respond to the week/range selector the way "Planned" does.

Known caveats

  • The Direction (Inbound/Outbound) filter only applies to Calls — Email and Webform tickets have no equivalent concept, so it's disabled outside the Calls channel.
  • A ticket can carry more than one Origin tag (e.g. a webform submission that also triggers an email) — each ticket is still counted once per matching channel, so Email + Webform totals can slightly exceed a simple sum if you're cross-checking against another report.
  • Avg Time to Resolution starts from a broader population than the rest of the page — when the channel is "All" it covers every Zendesk ticket, excluding the Product, Custom Reports Group, and Procurement groups, not just tickets tagged phone/email/webform. Selecting Calls/Email/Webform narrows it to that Origin tag specifically (Calls = phone-tagged tickets); the week selector scopes it the same way as every other KPI, bucketed by each ticket's created date (Pacific Time). Direction has no effect (tickets have no inbound/outbound concept). "Resolution" = time to first Solved status (Zendesk's first_resolution_time), not the final close — a reopened-then-resolved ticket is still measured from its first solve. A very recent week (or a low-volume channel) can show "—" since only tickets that have already been solved are counted — a ticket created this week but still open simply isn't in the average yet.

Refresh

  • Both pulls are incremental (checkpoint-based, since the last successful run) rather than a full re-pull each time, so a routine refresh only queries a day or two of new data.
  • This page is a static snapshot — automated daily refresh + republish keeps it current, but re-publish manually after any ad-hoc pipeline change.
